Ranking content pages for refresh review.

A FlyRank internship project that moved from task framing and a fixed rule to a grouped-split Logistic Regression model, evaluated with an operational top-of-list metric.

Problem

The content team cannot review every page at once. The useful decision is not simply whether a page is declining, but which pages should appear first in a limited review queue. I framed the project as a ranking problem so evaluation could focus on the top recommendations a team would actually inspect.

Task framing

The unit of analysis was one anonymized content page. I used is_declining_label as a proxy target and selected Precision@50 as the primary metric because false positives in the first 50 recommendations consume limited review time.

Honesty boundary: the label is a proxy for decline, not proof that a page should automatically be refreshed.

Baseline and signal audit

The first fixed rule selected pages with CTR below 0.07 and 90-day impressions above 731. It flagged 3,309 pages, with precision 0.675 and recall 0.137. This established a transparent benchmark but missed most proxy-positive pages.

In Week 4, I built a more operational rule using days since last update and impressions. The rule generated a ranked queue with the reason code STALE_VISIBLE, a confidence note, and a “could be wrong” check for every top recommendation.

Model design

I used a client-grouped train/test split to avoid placing pages from the same client in both sets. The train set contained 24 clients and 22,885 rows; the test set contained 8 clients and 7,115 rows, with zero client overlap.

The model was a Logistic Regression pipeline with preprocessing fit on the training data only. This gave me an interpretable learned benchmark without introducing a complex model before the evaluation setup was trustworthy.

The pure Logistic Regression model improved Precision@50 from 0.36 to 0.74. The eligibility-plus-model system preserved the locked staleness and visibility rule while improving the baseline queue, making it the recommended operational design when those guardrails are mandatory.

What I learned

A model can improve the ranking metric while still conflicting with operational eligibility. The strongest technical score is not automatically the strongest system. The right recommendation depends on whether the business wants maximum top-50 relevance or a queue that also stays inside locked review rules.

The next step is to validate the proxy against real content-review outcomes, test stability across time periods, and review model errors with domain experts.
